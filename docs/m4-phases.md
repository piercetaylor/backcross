# M4: implementation phases

This document decomposes milestone M4, the five items PLAN.md deferred past M3 (PLAN.md, end of the M3 verification block), into six phases in this repository, one commit each, plus three commits in the sibling `progeny-selector`, named S4, S5 and S6, that follow that repository's own `CLAUDE.md` and Python toolchain. Every commit passes the gates of CLAUDE.md. Written 2026-09-16 by the planner; the maintainer delegated every design decision under one criterion: best for academic and open-source plant-breeding users, meaning reproducible with standard tools (TASSEL, bcftools, the VCF specification, R and pandas exports), tolerant of spreadsheet exports, never silently wrong. Each decision is stated with its reason where it is taken, under a **Decision** label, so it can be lifted into the ADR the phase names. Every `[web]` citation is a page fetched today; a fact taken from `docs/research/cross-crop-genotype-conventions.md` (2026-09-14) is cited as `[research N]` with that file's reference number and its tag (`web`, `search`, `unverified`) repeated, since the research was not redone.

The doer of a phase makes no design decision. Where this file names a constant, a file, a signature, a token, a case or a message, that is the value. Where a fact could not be verified this session it says so instead of asserting it.

## 3. Phase 1: virtualisation of the graphical genotype view

Goal: the main canvas and its gutter lay out and draw only the rows inside the vertical scroll viewport (plus a small overscan), so draw cost is proportional to visible rows rather than to lines; and the overview represents every line, by binning lines into its pixel rows with the same majority rule the columns use, instead of drawing an evenly spaced subsample.

### 3.1 Decisions

- **Decision (D1.1): the genotype scroll container owns vertical scrolling.** Today the document scrolls (`.app-main` has no overflow, `shell.css` line 149) and `.geno-scroll` scrolls horizontally only. `.geno-scroll` gains `overflow-y: auto` and a token-bounded `max-height`, so the row window is computed from one element's `scrollTop` and `clientHeight`, with no window-scroll listener and no coupling to the shell's class names. Reason: a virtual list needs a scroll element with a known height; every virtual-list library (`react-window`, TanStack Virtual) takes one, and the document is the wrong one here because the marker-detail panel, legend and keyboard help sit below the plot. Under `@media print` the bound is removed and every row is drawn (section 3.5), as `tests/browser/print-media.test.tsx` already requires for the Lines table.
- **Decision (D1.2): the overview bins lines into rows, first stage, then markers into columns, second stage, and drops the subsample.** Each overview pixel row covers a contiguous run of lines in display order; at each marker its class is the majority among the run's called classes with `binning.ts`'s tie order, so every line contributes to the pixel row it falls in. Reason: ADR 0007's per-column majority is the tool's one rule for "more data than pixels"; applying it vertically is the same rule, whereas a subsample silently omits lines and fractional row heights would blend colours the palette does not contain. Two-stage binning (lines to rows, then rows to columns through the unchanged renderer) is not identical to a joint majority over the cell, and the ADR amendment says so; it costs one pass over `nLines × nMarkers(chrom)`, and the renderer, hit testing and textures stay unchanged.
- **Decision (D1.3): overscan is four rows on each side.** A constant in a pure module, not a token, because it is a count rather than a dimension.
- **Decision (D1.4): the overview leaves the scroll container.** It is a whole-chromosome locator and must stay visible while rows scroll; it moves to after `.geno-scroll` inside `.geno-plot`, indented by `--gutter-width` like the chromosome strip.

### 3.3 `row-window.ts` and the renderer

```ts
// src/ui/canvas/row-window.ts — pure, no DOM.
export interface RowWindow {
  /** Index of the first drawn row in the data's line order. */
  first: number;
  /** Number of drawn rows; first + count <= nRows. */
  count: number;
}
/** Rows drawn beyond each edge of the viewport, so a wheel tick never shows an undrawn row before the next frame. */
export const OVERSCAN_ROWS = 4;
/**
 * The rows intersecting [scrollTop, scrollTop + viewportHeight) at rowPeriod px per row, widened by
 * `overscan` rows each side and clamped to [0, nRows). A viewportHeight that is not a positive finite
 * number (an element that is not laid out, or print) means every row: { first: 0, count: nRows }.
 * rowPeriod <= 0 also means every row. nRows <= 0 gives { first: 0, count: 0 }.
 */
export function visibleRowWindow(
  scrollTop: number,
  viewportHeight: number,
  rowPeriod: number,
  nRows: number,
  overscan = OVERSCAN_ROWS,
): RowWindow;
```

Arithmetic: `first = max(0, floor(scrollTop / rowPeriod) - overscan)`; `end = min(nRows, ceil((scrollTop + viewportHeight) / rowPeriod) + overscan)`; `count = max(0, end - first)`. A negative `scrollTop` is treated as 0.

Renderer changes (`GraphicalGenotypeRenderer.ts`):

- New private field `rowWindow: RowWindow | null = null` and method `setRowWindow(window: RowWindow | null): void` (null means every row). Header comment's interface list gains it: `setRowWindow({ first, count } | null) — draw and hit-test only these rows; null (the default) is every row`.
- `draw()`: let `first = window?.first ?? 0`, `count = window === null ? nLines : min(window.count, max(0, nLines - first))`. `cssHeight = max(rowHeight, count * (rowHeight + rowGap))`. The row loop runs `for (let r = 0; r < count; r++)` over `data.lines[first + r]` at `y = r * (rowHeight + rowGap)`. The selection overlay height is `cssHeight` as today. Everything per column is unchanged.
- `hitTest(x, y)`: `row = floor(y / rowPeriod)`; return null when `row < 0 || row >= count`; the line is `data.lines[first + row]`. `yInRow` check unchanged.
- `setData` does not reset the window (the screen sets both before each draw).

### 3.4 `line-binning.ts`

```ts
// src/ui/canvas/line-binning.ts — pure, no DOM.
import type { GenotypeClassesLine } from '../../workers/protocol.ts';
/**
 * Bins `lines` (display order) into `nRows` synthetic lines. Row i covers lines
 * [floor(i * n / nRows), floor((i + 1) * n / nRows)); at each marker its class is
 * binning.ts's majorityClass over the counts of the covered lines' classes.
 * Returns `lines` itself when nRows >= lines.length (no copy) and [] when nRows <= 0 or lines is empty.
 * Every returned line's `classes` has the same length as lines[0].classes.
 * sampleId is `rows:${a}-${b}` with a and b the covered indices, inclusive, 0-based.
 */
export function binLinesIntoRows(
  lines: readonly GenotypeClassesLine[],
  nRows: number,
): GenotypeClassesLine[];
```

Implementation: one `Int32Array(6)` of counts reused per marker; per row, per marker, count the covered lines' class bytes, call `majorityClass(counts)`, write into a `Uint8Array(nMarkers)`. Cost `nRows × nMarkers × linesPerRow` = `nLines × nMarkers`.

## 5. Phase 3: vendor chunks and the bundle warning threshold

### 5.1 Decisions

- **Decision (D3.1): split `node_modules` into two vendor chunks with Rolldown's `output.codeSplitting` groups, and delete `build.chunkSizeWarningLimit` so Vite's default 500 kB warning is the threshold again.** ADR 0010 rejected a vendor chunk because it "improves neither download size nor time to interactive" and its only benefit, cache reuse across deploys, is weak. That is still true, and this phase does not claim otherwise. What changed is the reason for splitting: with one chunk, the warning threshold measures React Aria's size and had to be raised to 600 kB, which 0010 itself called "a setting that someone could raise again without thinking". With the dependencies in their own chunks, the entry chunk holds this repository's code alone (roughly 100 kB today: the 249.83 kB pre-React-Aria main chunk minus React and ReactDOM), Vite's default threshold is back in force, and it now measures what this repository adds. Lazy screens (0010's option 3) stay deferred with the same reasoning as 0010 gives; nothing here prevents them later.
- **Decision (D3.2): the option is `build.rolldownOptions.output.codeSplitting.groups`, not `manualChunks`.** Vite 8.2.2 bundles with Rolldown 1.2.7 (installed); `build.rollupOptions` "is an alias of `build.rolldownOptions`" [web] https://vite.dev/config/build-options; Rolldown's types say `manualChunks` "will be ignored" when `codeSplitting` is set and `advancedChunks` is deprecated in favour of `codeSplitting` (`node_modules/rolldown/dist/shared/define-config-*.d.mts`, `codeSplitting?: boolean | CodeSplittingOptions`, group fields `name`, `test`, `priority`; "it's recommended to use `[\\/]` to match the path separator").
- **Decision (D3.3): side-effect order is not a risk for these groups.** ADR 0010 quoted Rollup's warning that a shared chunk "can change the behaviour of the application if side effects are triggered before the corresponding modules are actually used". The entry imports React, ReactDOM and React Aria before any app module runs (`src/main.tsx`), so every vendor side effect already precedes app code; the groups reproduce that order.
- **Decision (D3.4): a bundle check with fixed byte limits runs inside `npm run build`.** No node test runs after a build, so the acceptance is a script in the build gate and therefore in CI's `check` job.
- **Decision (D3.5): no claim about cache reuse is recorded until measured.** GitHub Pages is widely observed to serve with `Cache-Control: max-age=600`; the doer runs `curl -sI` on the deployed site's `assets/` URL if `ENABLE_PAGES` is on, else records "not measured", in the ADR.

## 6. Phase 4: contract 1.3.0, lines and rows

Goal: both repositories read blank lines, `#` lines and quoted line breaks the same way, and the contract says which way. The sibling already behaves as the contract will state on every point but two (a blank line before the header, and the delimiter sniff on line 1); this repository changes on every point.

### 6.1 Decisions

- **Decision (D4.1): `#` is not a comment marker in any input.** R's `read.csv` (`comment.char = ""`), `readr::read_csv` (`comment = ""`) and pandas `read_csv` (`comment=None`) treat a `#` line as data by default; bcftools rejects a `#` line after the VCF header; TASSEL's HapMap reader reads line 1 as the header. This repository's silent skipping of `#` rows in the wide CSV, samples.csv and markers.csv, and its scan for the `rs#` line, would drop or misread lines that every standard tool keeps. In VCF, `##` lines and `#CHROM` are the header as the specification defines them; any other `#` line after `#CHROM` is a data line with the wrong field count and is an error. In HapMap the header is the first line that is not blank. In the three delimited files a row beginning with `#` is a row.
- **Decision (D4.2): a blank line is skipped wherever it occurs, including before the header, and so is a delimited row whose every field is empty or whitespace.** "Blank" means empty or holding only spaces and tabs. Spreadsheets and hand edits leave such lines; they carry no data, so skipping them is not silent loss, and it generalises 1.2.0's all-empty wide-CSV row to every input. The header is the first line that is not skipped, and the delimiter sniff reads that line. The sibling's VCF and HapMap readers already skip blank body lines; its HapMap, wide-CSV and manifest readers do not skip a blank line before the header and change in S4.
- **Decision (D4.3): a quoted field may contain a line break, in all three delimited files (RFC 4180 section 2, rule 6 [web] https://www.rfc-editor.org/rfc/rfc4180).** Excel writes a quoted line break for a cell containing one, which a `notes` column invites; Python's `csv` (the sibling) and readr read them. This repository's `forEachRow` splits on `\n` before quoting and must extend a physical line while its quote count is odd. Error messages that name a line name the row's first physical line here and the last in the sibling (`csv.reader.line_num`); line numbers are not contract vocabulary and stay as each repository writes them.
- **Decision (D4.4): a row with more than one fault reports one of them; which one is unspecified, and no case carries two faults.** Aligning the check order across two parsers buys nothing a user can act on: either message names the line, and fixing one fault reveals the other.
- **Decision (D4.5): new error kind `genotypes.column_count`** for a data line whose field count differs from the header's, which the `#`-after-header VCF case needs and which both repositories already emit under their own wording.
- **Decision (D4.6): `MAX_CONTRACT_BYTES` becomes 128 KiB.** `contract/` is 61,095 bytes; this phase adds about 10 KB and phases 5 and 6 about 20 KB. The cap exists to keep the mirror small enough to copy by hand and review; 128 KiB still is.

## 7. Phase 5: contract 1.4.0, named token profiles

Goal: a named, machine-readable token profile under `contract/profiles/` changes how HapMap and wide-CSV cells are read, is chosen on the Upload screen, the CLI and the sibling's Load screen and CLI, and is recorded in every export.

### 7.1 Decisions

- **Decision (D5.1): a profile is a JSON document with four vocabularies and a base flag, keyed by platform, never by crop.** The research found every token difference traces to a platform or format, none to a crop [research, verdict], so the profile axis is platform; the crop scheme (phase 6) is a separate axis and carries no tokens.
- **Decision (D5.2): profile tokens take precedence over the format's core vocabulary; `base: "nucleotide"` keeps the core underneath, `base: "none"` replaces it.** SoyBase's report is nucleotides plus `H` and `U`, so it layers; DArT's `0/1/2/-` and Axiom's `AA/AB/BB/NoCall` are complete vocabularies, so they replace.
- **Decision (D5.3): a heterozygote token that names no alleles (`H`) resolves to the marker's two alleles seen on that row (HapMap's `alleles` column included); with any other number of alleles it is an error naming the cell.** With two alleles observed the pair is determined; with one the second allele is unknown and inventing it would be silently wrong; with three the token is ambiguous. Error kind `genotypes.ambiguous_heterozygote`.
- **Decision (D5.4): a profile other than the default is an error with a VCF or a BrAPI source**, kind `genotypes.profile_format`, because GT indices carry no tokens and silently ignoring a chosen profile would be wrong.
- **Decision (D5.5): the profile is recorded as a trailing `token_profile` column in every per-line and pairwise CSV export and as a "Token profile" row in the report's dataset summary.** Appended last so readers that pick existing columns by position are unaffected, unlike ADR 0015's insertion; the summary CSV's per-chromosome columns already made its tail variable, so nothing positional is lost. A user-supplied profile is recorded as `custom:<id>`; the absence of a profile as `default`.
- **Decision (D5.6): auto-detection of A/B/H coding runs only under the default profile or a `base: "nucleotide"` profile, and cells the profile claims (its missing, homozygous and heterozygous tokens, compared upper-cased) do not vote; a `base: "none"` profile fixes nucleotide-family mode.** A `dart` file is all `0/1/2/-` and would otherwise be tested for coded letters it cannot contain; an Axiom file's `AA/AB/BB` fails the coded test as today and reaches the profile. Under `soybase-report` a file whose cells are only `A`, `H` and `U` (the donor allele absent at every marker of a small file) must not be read as coded: `H` and `U` are the profile's tokens, so only `A` votes, no `B` or `H` is seen, and the file is nucleotide.
- **Decision (D5.7): five built-in profiles: `tassel`, `soybase-report`, `dart`, `axiom`, `kasp`.** The four named by the maintainer (ADR 0014) plus KASP SNPviewer, whose `X:X`/`X:Y`/`?` collides with TASSEL's `X` [research 1, 4, both web] and is common in marker-assisted backcrossing labs; `illumina` (GenomeStudio `AA/AB/BB/--`) is covered by `axiom` with `--` added to its missing list, and the profile says so in its description. Tokens marked `[search only]` in the research (DArT, Axiom) are recorded as the maintainer's or research's reading, not verified against the vendor's document.

### 7.2 Profile files (`contract/profiles/<id>.json`, exact contents, two-space indent, LF, trailing newline)

Schema (documented in `data-contract.md`, 7.3): `id` (`^[a-z0-9][a-z0-9-]{0,31}$`), `name` (non-empty), `description`, `base` (`"nucleotide"` or `"none"`), `homozygous` (object: token → allele symbol, symbol matching `^[^\s]+$`), `heterozygous` (object: token → `[symbol, symbol]` or `"*"`), `missing` (array of tokens), `sources` (array of strings). Tokens are compared case-insensitively after trimming; the three token sets must be pairwise disjoint after upper-casing; with `base: "none"`, `homozygous` must be non-empty and `missing` must contain `""`.

## 8. Phase 6: contract 1.5.0, crop chromosome schemes

Goal: a crop selected on the Upload screen, the CLI and the sibling's Load screen and CLI chooses the chromosome scheme (which spellings normalise to which canonical names, and their order); soybean is the default and reproduces 1.2.0 exactly; the crop is recorded in every export.

### 8.1 Decisions

- **Decision (D6.1): a crop scheme is a JSON document with an ordered list of canonical chromosome names, a parallel list of keys, and one alias regular expression whose capture groups yield the key.** The research asked for per-assembly alias tables [research, consequence 1]; this first release ships one alias pattern per crop that unifies the verified spellings, and the file has an `assembly` field naming the reference the canonical spelling comes from so a second assembly can be added as a second file later. Key derivation: join the defined capture groups, upper-case, strip leading zeros from each digit run (`0+` before a digit); look the key up in `keys`; a miss keeps the name as written and orders it after the canonical names in natural order, exactly the 1.2.0 rule. A name that matches nothing is never changed, so unanchored bins (`ChrUn`, `chrUn`, `Un0`, `chr00`) and organelles (`MT`, `Pltd`, `Mt`, `Pt`) pass through, [research, consequence 4].
- **Decision (D6.2): `soybean.json` is the 1.2.0 pattern verbatim (`gm|chr|chromosome|lg` prefixes, 1..20) and is the default; every other scheme accepts only `chr` and `chromosome` prefixes.** The `LG` prefix is a soybean concession from 1.1.0; in other crops a linkage-group number need not equal a chromosome number, so accepting it would be silently wrong.
- **Decision (D6.3): first release ships nine crops: soybean, maize, rice, sorghum, wheat, barley, oat, common bean, cotton.** Cowpea (`Vu01(old4)` renumbering [research 35, web]), pea (`1LG6`, chromosome number differs from linkage group [research 36, web]), sunflower (two live assemblies with the assembly baked into the name [research 38, 39, web]) and peanut (names `[search]` only [research 31]) are deferred to a later version because a bare number is ambiguous in each, and a scheme that guessed would be silently wrong; potato is dosage and out of scope [research 41]. The canonical spelling per crop is the `[web]`-verified one where the research has it and the doer records the others as this plan's decision.
- **Decision (D6.4): the scheme is chosen at load time, lives on the `Dataset` as `crop` (its id), and every later normalisation (`markers.csv`, target regions, BrAPI `referenceName`) uses it.** The worker answers `targets` requests from the resident dataset, so the scheme must travel with it.
- **Decision (D6.5): a trailing `crop` column in every per-line and pairwise CSV export, after `token_profile`, and a "Crop" row in the report**, for the same reason as D5.5.
- **Decision (D6.6): no ploidy flag beyond an informational `ploidy` field.** Every shipped crop is diploid-called (allopolyploids on subgenome-specific markers [research, consequence 6]); the contract already states diploid calls only, so a flag would decide nothing.

### 8.2 Scheme files (`contract/crops/<id>.json`)

Schema: `id`, `name`, `species`, `ploidy` (integer), `assembly` (string), `chromosomes` (canonical names in order), `keys` (parallel, upper-case, no leading zeros), `pattern` (JavaScript/Python-compatible regular expression source, applied case-insensitively to the trimmed name, anchored by the pattern itself), `sources` (strings). `chromosomes.length === keys.length`, keys unique, `pattern` compiles in both `RegExp` and `re`.

### 8.7a Correction, 2026-09-22: the `crop` column's position and the results schema

The S6 table above says `io/export.py` gains a "trailing `crop` key", and section 8.6 says the
sibling's outputs "gain the trailing `crop` column". For `progeny-selector` that is wrong, and the
doer of S6 follows this note where the two disagree.

`progeny-selector/docs/adr/0016-results-schema-freeze.md` line 29 fixes the position: a new fixed
column goes after `results_schema` and before `token_profile`, which stays last. The rule is
load-bearing in the R reader, which commit `2b966bc` corrected to expect `token_profile` last and
not in the fixed prefix. A `crop` column written after `token_profile` would break
`scripts/read_results.R` and any reader that takes the last column as the token profile.

S6 therefore makes four edits the table does not name:

1. `src/progeny_selector/io/export.py`: insert `"crop"` into `FIXED_COLUMNS` and
   `SELECTION_COLUMNS` between `"results_schema"` and `"token_profile"`.
2. `src/progeny_selector/constants.py` line 171: `RESULTS_SCHEMA` becomes `"1.1.0"`. ADR 0016
   line 29 makes a new fixed column a minor bump.
3. `tests/test_results_schema.py`: `FIXED_PREFIX` grows to 35 entries and the `len(FIXED_PREFIX)
   == 34` assertion at line 79 becomes 35. `EMPTY_HEADER` keeps its shape, since `crop` enters the
   prefix and `token_profile` still trails it.
4. `scripts/read_results.R` lines 45 and 89: add `crop` to the column list and
   `crop = col_character()` to the `col_types` specification.

No earlier version is in error. ADR 0016 was committed at `419a4c5`, after contract 1.4.0 landed at
`17464e3`, and its text names `token_profile` as part of the frozen 1.0.0 prefix. Schema 1.0.0 was
frozen with that column already present, so S5 owed no bump and none was missed.

This correction is confined to `progeny-selector`. A search of `docs/adr` and `docs/data-formats.md`
in this repository finds no rule reserving the last export column, so phase 6's own outputs take the
trailing `crop` column as section 8.6 specifies, and 8.6 stands unamended for this repository.

The ADR number in the S6 table is also wrong. `docs/adr/0015` in `progeny-selector` is the assembly
selector. The crop schemes take `0020` there, the next free number, matching `0020` in this
repository as `docs/handoff-m4-phase6.md` records.
