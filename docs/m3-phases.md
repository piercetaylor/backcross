# M3 hardened: implementation phases

This document decomposes milestone M3 (PLAN.md, "Milestones") into five phases in this repository, one commit each, plus two commits in the sibling `progeny-selector` that are named as such and follow that repository's own `CLAUDE.md` and Python toolchain. Every commit passes the gates of CLAUDE.md. The four decisions the maintainer took on 2026-09-12 (Vitest browser mode with Playwright on Chromium and Firefox; BrAPI developed against the public test server and recorded as a synthetic fixture; the sibling may change in its own commits; ADR 0010's 600 kB threshold with no chunk split) are taken as given. This file adds only what an implementer needs to make no further design decision; where a fact could not be verified this session it says so instead of asserting it.

Dates in this file are 2026-09-12. Every `[web]` citation is a page fetched today. The M2.5 verification block in PLAN.md ("Not verified", "Deferred") is M3's inheritance and is allocated phase by phase below.

## Invariants that every phase respects

1. `src/core/` stays pure: no DOM, no fetch, no filesystem. `fetch` lives in `src/io/brapi.ts` and is called from the worker; `src/io/` may read streams and bytes but computes nothing.
2. The worker owns the genotype matrix and never sends it back (docs/adr/0001). The streaming loader (phase 2) parses inside the worker; the BrAPI loader (phase 4) fetches inside the worker. No result shape gains raw alleles.
3. No documented column, parameter name or output format changes silently. From phase 3 the shared input contract is a versioned document plus fixtures under `contract/`; any change there bumps `contract/VERSION`. Proposed vocabulary changes are listed under "Questions" and are not made until answered.
4. Never commit real genotype data. The 50K × 200 benchmark input is generated inside the test run and never written to the repository. `tests/fixtures/synthetic/` stays under 200 KB; `tests/fixtures/brapi/` (phase 4) is generated by the same script and stays under 64 KB; `contract/` stays under 64 KB.
5. The ADR 0009 open question on filling intervals between disagreeing markers stays open. `fillBetweenMarkers` in `src/ui/canvas/binning.ts` is not modified.
6. No AI attribution in any commit or pull request, in either repository.
7. Four gates plus the fixture gate before every commit. Phase 1 widens the fixture gate to `git diff --exit-code -- tests/fixtures contract` in `ci.yml` and CLAUDE.md, so every generated directory this milestone adds is covered by "edit the generator, never the files".
8. `tests/**` node tests keep `environment: 'node'` and `npm test` keeps meaning the node project alone; browser-mode tests live only under `tests/browser/` and `tests/bench/`, the node project excludes those directories, and they run through `npm run test:browser` and `npm run test:bench`.
9. Virtualisation (drawing more lines than the overview has pixels) is not in M3's scope as PLAN.md states it; the 200-line benchmark exercises the overview's subsampling path and records its timing, nothing more.
10. Conventional Commits; phases 2, 4 and 5 add `CHANGELOG.md` entries under `[Unreleased]`; phase 3 adds a "Changed" entry for the contract pointer; phase 1 adds none.

## Six resolutions

1. **Memory is measured with `performance.measureUserAgentSpecificMemory()`**, which returns `{ bytes, breakdown[] }` and "includes JavaScript and DOM memory of all iframes, related windows, and web workers in the current process" [web] https://web.dev/articles/monitor-total-page-memory-usage, so the worker that holds the matrix is inside the figure; it is Chromium-only (Chrome 89+, same page; MDN marks it not Baseline [web] https://developer.mozilla.org/en-US/docs/Web/API/Performance/measureUserAgentSpecificMemory) and throws `SecurityError` unless `crossOriginIsolated`, which needs COOP and COEP response headers that Vite's `server.headers` can set for the test server [web] https://vite.dev/config/server-options but GitHub Pages cannot, so the measurement is test-only. Firefox gets an accounting assertion only (resolution 2). Whether Vitest's tester iframe survives `Cross-Origin-Embedder-Policy: require-corp` was not verifiable from documentation; phase 1 carries a probe test and a fixed fallback.
2. **"Under twice the file size" is defined against inflated bytes**, counted by the streaming parser and returned as `bytesInflated` in the `loaded` result, because the bound is unsatisfiable against a compressed size: the allele arrays alone are 2 bytes per call and a bgzipped GT column is a fraction of that. Two figures are asserted: resident memory after load (what the API sees) and the parser's own peak accounting (`peakBuilderBytes`, what the API cannot see mid-parse). Q1 lets the maintainer veto the definition.
3. **The benchmark input is generated at test time** by `tests/support/synth-vcf.ts`, a deterministic mulberry32 generator sharing its design with `scripts/make-fixture.mjs` but living in TypeScript so the browser test can call it; the text is assembled as a `Blob` of line chunks and bgzip-framed by `tests/support/bgzf.ts`, never written to disk, so nothing is committed and the 200 KB limit is untouched.
4. **bgzip streams through the existing `fflate` dependency, no new dependency.** fflate's streaming `Gunzip.push(chunk, final)` buffers arbitrary chunk boundaries and, when a member ends with input remaining, resets state and continues into the next member (multi-member support since 0.8.0 per its CHANGELOG [web] https://raw.githubusercontent.com/101arrowz/fflate/master/CHANGELOG.md); its header parser skips the FEXTRA field bgzip uses (`if (flg & 4) st += (d[10] | d[11] << 8) + 2` [web] https://raw.githubusercontent.com/101arrowz/fflate/master/src/index.ts). The platform alternative, `DecompressionStream('gzip')`, is ruled out because the spec says "A gzip stream may only contain one member" and trailing data is a `TypeError` [web] https://compression.spec.whatwg.org/.
5. **Contract version is SemVer in `contract/VERSION`, canonical copy in this repository, drift detected by hash.** Major for a changed or removed column, vocabulary token or rule; minor for an additive optional column or token; patch for wording. `contract/MANIFEST.sha256` lists every file's hash; each repository's test recomputes the hashes and compares, and asserts the version string appears verbatim in its `docs/data-formats.md`; a local script byte-diffs `contract/` against the sibling checkout. Drift already exists between the two documents (see phase 3), which is why cases assert only what both repositories do when each test lands.
6. **BrAPI uses `GET /callsets`, `GET /variants` and `GET /allelematrix`** (v2.1, module Genotyping) and produces a `ParsedGenotypes` through the same `GenotypeBuilder` the VCF parser uses, so `assembleDataset` and everything downstream are untouched. Verified against the public test server today: `/allelematrix` honours `dataMatrixAbbreviations=GT` and the `dimensionVariantPage*`/`dimensionCallSetPage*` parameters and returns `callSetDbIds`, `variantDbIds`, `dataMatrices[{dataMatrixAbbreviation, dataMatrix}]`, `pagination[{dimension: 'VARIANTS'|'CALLSETS', page, pageSize, totalPages}]`, `sepPhased`, `sepUnphased`, `unknownString`, `expandHomozygotes` [web] https://test-server.brapi.org/brapi/v2/allelematrix?variantSetDbId=variantset1&dimensionVariantPage=1&dimensionVariantPageSize=3&dimensionCallSetPage=0&dimensionCallSetPageSize=2&dataMatrixAbbreviations=GT. The Variant schema defines `start` as "The start position at which this variant occurs (0-based)" [web] https://raw.githubusercontent.com/plantbreeding/BrAPI/brapi-V2.1/Specification/BrAPI-Genotyping/Variants/Schemas/Variant.yaml, so `pos_bp = start + 1`. The test server returns `null` for `referenceName`, `start` and `referenceBases` [web] https://test-server.brapi.org/brapi/v2/variants?pageSize=2, so the loader must accept positions from `markers.csv` and synthesise allele symbols from indices when bases are absent.

bgzip framing (`tests/support/bgzf.ts`): `bgzfBlocks(bytes: Uint8Array, blockBytes = 0xff00): Uint8Array[]` compresses each block with fflate `gzipSync(block, { mtime: 0 })`, sets FLG bit 2 and splices an 8-byte extra field after the 10-byte header (XLEN=6 LE, `'B'`, `'C'`, SLEN=2 LE, BSIZE = total member length − 1 LE); the gzip CRC32 and ISIZE cover only the uncompressed data, so the splice needs no recomputation (fflate exports no CRC). The BGZF definition, the 64 KiB per-block bound and the 28-byte EOF block `1f 8b 08 04 00 00 00 00 00 ff 06 00 42 43 02 00 1b 00 03 00 00 00 00 00 00 00 00 00` are from the SAM specification source [web] https://raw.githubusercontent.com/samtools/hts-specs/master/SAMv1.tex; `BGZF_EOF` is exported as that constant and appended. A file produced by htslib's `bgzip` is not available in this environment; `tests/bgzip-real.test.ts` (node project) runs only when `process.env.BGZIP_BIN` names a binary and is otherwise skipped with that reason.

## Phase 2: streaming bgzipped-VCF parse in the worker

Goal: the worker receives the `File`, inflates and parses it chunk by chunk, and never holds the inflated text; peak and resident memory are below twice the inflated size.

Arithmetic the implementer works against, for 50K × 200 (10^7 calls): allele arrays 2 bytes per call = 20 MB; VCF text at least 4 bytes per call (`0/1\t`) so `bytesInflated ≥ 40 MB`. In `GenotypeBuilder` the doubling growth holds up to 2 × size per array and `finish()` slices both, so the parse peak is at most 6 size-units = 60 MB; `subsetColumns` in `assembleDataset` holds `parsed` and the subset together, 40 MB; the classification adds one byte per candidate-marker, 10 MB, and the Graphical genotypes screen's `classes` request copies the same 10 MB to the main thread. Resident after load is about 45 MB and peak about 60 MB against a bound of 80 MB. The lever, if the measured figure is over, is the growth factor in `push` (1.5 caps the peak at 5 size-units); no other change is authorised in this phase. The current path, by contrast, holds the compressed buffer, the inflated `Uint8Array`, the decoded string and the per-line `split` arrays at once, which is what phase 1's baseline should show exceeding the bound.
