# Design survey: how comparable tools look and behave today

Scope: evidence beyond docs/design-brief.md. The brief already surveys Flapjack, Germinate, Galaxy, Geneious, SnapGene and JBrowse 2 for layout, typography, colour, shape encoding, density and components; none of that is repeated here. This document looks at genotype/haplotype matrix viewers the brief does not cover, at cBioPortal's OncoPrint specifically, and at a few adjacent dense-data tools whose table-plus-visualisation pattern is worth stealing. Genotype class colours are fixed by docs/adr/0007 and are not reopened; everything here is shape, layout, legend and interaction.

## OncoPrint (ComplexHeatmap's `oncoprint()`, and cBioPortal's own view)

What it is: the standard plot for showing per-sample, per-gene categorical alteration calls as a matrix of coloured glyphs, one row per gene and one column per sample. Two things were checked directly: the R reference documentation for `ComplexHeatmap::oncoprint()`, which defines the plot form [web] https://jokergoo.github.io/ComplexHeatmap-reference/book/oncoprint.html, and cBioPortal's own FAQ, which documents interaction on the live tool [web] https://docs.cbioportal.org/user-guide/faq/. (`oncoprintjs`, the JS renderer cBioPortal itself ships, has moved into the cbioportal-frontend monorepo and its README states its own API documentation is not yet written, so nothing below is drawn from it.)

The glyph mechanism is the one genuinely new idea here relative to our texture-per-class approach. A cell is not one flat colour; it is a stack of rectangles drawn back to front. A plain grey background rectangle fills the whole cell first (this is also how "not profiled for this gene" reads, distinct from a called-but-unaltered cell, which cBioPortal's FAQ confirms is tracked and displayed differently from a true negative). Foreground rectangles for each co-occurring alteration are drawn on top at different height fractions of the cell — a large one, filling most of the cell height, for the primary call, and a smaller one, filling a minority of the height, for a secondary attribute recorded on the same sample. Because the small rectangle only covers part of the cell, both remain visible when they coincide. This is a mechanism for showing two facts in one cell that our split-diagonal heterozygote texture cannot: our texture already spends its one channel on a fixed vocabulary of six classes, so it cannot also flag, say, "call disagrees between duplicate marker probes" or "coverage below threshold" without a seventh visual state. A thin foreground bar at a fixed height fraction, drawn only when the flag is set, could carry that without touching the class colour.

The legend is generated directly from the same rule set that draws the cells, so class name and glyph never drift apart; this is a property of the implementation, not a placement (the documentation does not say where on the page the legend sits). Column and row order are not fixed to input order: rows sort by how often each gene is altered across the sample set, and columns can be sorted by a "memo sort" that groups samples to make co-occurring or mutually exclusive alterations visually contiguous, rather than by a single scalar. cBioPortal's live tool adds two interactions not in the R package: a gene track can be dragged by its name, or moved via a three-dot menu next to the name, to reorder rows by hand; and hovering a sample cell shows which sequencing panel that sample was profiled on, with a click-through to the gene list for that panel.

Transfer: the layered-glyph idea is the most exportable thing in this survey, because it solves a problem the brief leaves open — flagging a per-cell qualifier without adding a seventh class colour — and is compatible with the retained-mode canvas renderer already built (ADR 0007), since it is still one draw call per cell, just two rectangles instead of one. The memo-sort idea (order columns to make a pattern visually contiguous) is a genuinely different sort key from anything the RPP-based sorts in docs/adr/0006 produce and would suit a "cluster lines by shared donor segment" view. The three-dot per-row reorder handle and drag-to-reorder gene tracks transfer directly to letting a breeder manually pin a chromosome or a specific line's row above the rest without leaving the canvas.

## Morpheus (Broad Institute)

What it is: a general-purpose in-browser heatmap tool for genomic matrices, documentation read directly [web] https://software.broadinstitute.org/morpheus/documentation.html. Not genotype-specific, but its interaction model for a big categorical-or-continuous matrix is close to ours.

Row and column annotations are attached as thin coloured tracks alongside the main matrix rather than as separate charts, and a user chooses per-annotation whether it renders as text, a solid colour, or a small bar chart, by right-clicking the annotation's header — the control lives on the axis it affects, not in a separate panel. Sorting is by clicking an annotation header, and shift-click sorts by multiple annotations in sequence (a stable multi-key sort), which is a control gesture our Lines table does not currently offer and R users will already expect from `dplyr::arrange`. Double-clicking inside the matrix offers three reorderings: strict ascending, strict descending, or a similarity-based ordering that groups similar rows or columns together without a predefined key. Groups created by sorting or clustering are separated by a visible gap of blank space rather than a rule line, which is a lighter-weight group divider than a border.

For finding specific items in a large matrix, a search box accepts multiple terms and marks every matching row or column with a small tick mark on the scrollbar track itself, so a user scanning a scrollbar sees where their matches are before scrolling to them; a "Matches to Top" action then reorders the view so all matches are visible together.

Transfer: the scrollbar tick marks are a concrete answer to a problem neither the brief nor Flapjack's live-count readout solves — showing where the rows or columns a user cares about are, not just how many are visible — and would sit naturally on the Lines table's vertical scrollbar once row virtualisation exists (PLAN.md's M3 item). Shift-click multi-column sort is a small, well-understood addition to the table. The annotation-track-as-colour-or-bar-chart choice, and the on-axis-header control placement, both transfer to any per-chromosome summary track placed above the graphical genotype matrix (the brief's `docs/adr/0007`-referenced chromosome summary row is exactly this kind of track).

## GenoSee

What it is: a 2024 open-source graphical-genotype plotting tool aimed at exactly this application (phased and unphased marker calls across chromosomes for multiple samples), read from its methods paper [web] https://pmc.ncbi.nlm.nih.gov/articles/PMC11780333/. It ships as a command-line tool and a notebook interface with dropdown mode and colour pickers, not a persistent web app, so its layout conventions are thin, but its density-handling decision is concrete and directly on point.

Each chromosome is drawn as two adjacent narrow rectangles rather than one, so that two haplotypes can be shown independently when the input is phased; for unphased calls this collapses to one rectangle and does not add anything our single-track design does not already do. The relevant decision is a `--fill` toggle: with fill on, the interval between two markers is coloured, matching our own approach (docs/adr/0007); with fill off, only a thin line is drawn at each marker's exact position and the space between is left blank. The paper's own guidance is to turn fill off once a chromosome carries more than roughly 100 markers, on the reasoning that a filled interval between sparse markers overstates precision.

Transfer: this is not a new layout idea but it is new evidence for the open question both the brief and ADR 0009 record and leave unsettled — whether filling the interval between markers asserts more than the data supports. GenoSee's answer is to make it a density-triggered toggle rather than a fixed choice, with a specific numeric threshold, which is a more actionable middle path than "fill only where flanking markers agree." The two-rectangle phased layout does not transfer, since this application's marker calls are unphased ABH/parent-of-origin classes, not haplotypes.

## Helium (James Hutton Institute)

What it is: a pedigree visualisation tool from the same group that built Flapjack, read from its BMC Bioinformatics paper [web] https://pmc.ncbi.nlm.nih.gov/articles/PMC4133633/. It draws pedigrees, not genotype matrices, but its screen layout is a three-panel pattern worth naming because it differs from Flapjack's own (which the brief already covers): a main pannable, zoomable view; a static overview panel that never changes with interaction and exists purely for orientation in a large dataset; and a details panel that shows on-demand passport and background data for whatever is currently selected, pulled from Germinate. Data overlays (phenotype or genotype values drawn onto the pedigree) are chosen from a set of tabbed panes rather than a single dropdown, and nominal categories are separated from ordinal ones by using hue for the former and saturation steps of one hue for the latter. A separate "local view" lets a user pick one line and a number of ancestor and descendant generations to show, dropping everything else from the drawing rather than dimming it.

Transfer: the static-overview-plus-live-detail split is close to what docs/design-brief.md already specifies for the genotype canvas (a scaled whole-chromosome overview plus the interactive matrix), so this mostly confirms rather than adds. What is new is the local-view filter: instead of a live count of hidden rows (Flapjack's answer, already in the brief), Helium removes context entirely on request and lets the user dial back in by generation count. That is a different, complementary answer to "too much data to show at once" from "tell the user how much is hidden" — it is "let the user shrink the universe on demand" — and could apply to a "show only this line's chromosome plus its two declared parents" view on the Compare screen.

## UCSC Genome Browser track configuration

What it is: the track display and configuration model of the desktop-era but still-current UCSC browser, read from its user's guide [web] https://genome.ucsc.edu/goldenPath/help/hgTracksHelp.html. Every track (not just genotype tracks) has five display modes chosen per track: hidden; dense, which collapses every feature in the track onto a single line regardless of overlap; squish, features at half height, unlabelled, several per line; pack, each feature separately labelled but sharing lines where it fits; and full, one feature per line, which the guide itself warns against using when a region is feature-dense because of the vertical space it costs. Configuration — including which of these modes a track uses — is reached by right-clicking directly on the track's rendered data, which opens a small popup scoped to that track, rather than through a separate settings panel elsewhere on the page. Separately from the user's manual choice, the browser has an automatic fallback: past 250 features in the visible region it forces a tighter display mode on its own rather than letting the track become unreadable, and tells the user to zoom in or filter to get back to their preferred mode.

Transfer: the named, ordered set of density levels (rather than a binary compact/comfortable toggle) is more granular than what the brief specifies for the Lines table, and the automatic-downgrade-past-a-feature-count behaviour is a concrete, numeric answer to "what happens when there is more data than the chosen density can show," which neither the brief nor Flapjack's live-count readout addresses — the count readout says how much is hidden by a filter, not what happens when nothing is filtered and there is simply too much on screen. Right-click-on-the-data-to-configure-that-row is a smaller, more targeted alternative to a persistent toolbar, worth considering for a single chromosome track in the genotype view (rendered as canvas pixels, right-click is available for free) but not for the Lines table, where React Aria's grid pattern already claims right-click for cell context menus.

## Galaxy dataset actions in the history panel

What it is: the per-dataset action row in Galaxy's history panel, read from its own documentation [web] https://galaxyproject.org/learn/managing-datasets/. This is additional to what the brief already cites about Galaxy (its left activity bar for navigation); this is about the linked table-to-visualisation pattern for one item, not the page-level layout. Each dataset entry in the history list carries a fixed row of icon actions in its lower-left corner: download, view details, rerun the job that produced it, and, when applicable, open it directly in one of several external or built-in viewers. The rerun and view-details actions sit on every dataset row regardless of type; the viewer links appear only for datatypes that support them.

Transfer: this is a smaller-grained version of the table-canvas link the brief already specifies for the Lines table and the graphical genotype (sorting either reorders both). What it adds is per-row, not per-view: a fixed action affordance on every table row that jumps straight to that item's rendering elsewhere on the page, which our Lines table does not yet have a stated equivalent for (there is no "view this line's genotype" action documented per row, only a shared selection state).

## What this adds to docs/design-brief.md

Ranked by expected benefit to the Lines table and the graphical genotype view, counting only what is new relative to the brief:

1. **A layered second glyph on a cell, at a fixed height fraction, for a per-cell qualifier flag** (OncoPrint). This is the highest-value addition because it is a mechanism, not a one-off tweak: it gives the genotype view a way to flag things like probe disagreement or low-confidence calls without consuming a class colour or fighting with the heterozygote texture, and it costs one extra rectangle per flagged cell in the existing canvas renderer.
2. **An automatic, numeric-threshold fallback to a denser display mode when a track has more features than pixels can show clearly** (UCSC's 250-feature rule; GenoSee's ~100-marker-per-chromosome fill-off rule as corroborating evidence for the brief's own open question). The brief's live-count readout tells a user how much a filter hides; neither it nor anything else in the brief says what happens when nothing is filtered and there is simply too much data, which is the normal case for a whole-genome view.
3. **Scrollbar tick marks for search or selection matches, plus a "bring matches together" action** (Morpheus). Concrete and small to build once the table is virtualised, and answers a question the brief does not: not how much is hidden, but where the rows a user is looking for currently are.
4. **Shift-click multi-column sort on the table** (Morpheus). A one-line addition to the sort model already planned, and matches a gesture R-fluent users already have from `dplyr::arrange` with multiple keys.
5. **A column-clustering sort key that groups samples by shared pattern rather than by a single scalar** (OncoPrint's memo sort). Genuinely different from the RPP-based sorts in docs/adr/0006, useful specifically for a "which lines share this donor segment" question the Compare screen is meant to answer.
6. **A per-line, per-row jump to that line's rendering elsewhere on the page** (Galaxy). The brief's shared-selection model covers the reverse direction (select in canvas, see it in the table); a direct per-row action is the missing forward direction.

Not included: Helium's overview-plus-detail split and its context-shrinking local-view filter are close enough to what the brief already specifies (the scaled whole-chromosome overview, the live hidden-row count) that they confirm rather than extend it. The "no-data cell keeps its background but is distinct from a true negative" distinction that OncoPrint documents is already what ADR 0007 does with missing-as-white versus uninformative-as-grey; OncoPrint is corroboration, not a new decision. Nothing retrieved here addressed how any of these tools visually communicate that a filter is hiding rows beyond what Flapjack's live count (already in the brief) does.
