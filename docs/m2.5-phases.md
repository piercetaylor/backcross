# M2.5 interface: implementation phases

This document decomposes milestone M2.5 (PLAN.md, "Milestones") into five phases. Each phase is one commit, and each commit passes the same gates. The decisions come from docs/adr/0009 and the reasoning from docs/design-brief.md; this file adds only what an implementer needs to make no further design decisions. Where it departs from either document it says so, and the departures are collected at the end.

Dates in this file are 2026-09-11. Contrast ratios were computed with the WCAG 2.x relative-luminance formula from the hex values in src/core/palette.ts and the ramp below; every figure quoted here is reproduced by the tests named in the phase that introduces it.

## Invariants that every phase respects

These are restated from CLAUDE.md, PLAN.md and the ADRs so that a phase can be implemented without re-reading them.

1. `src/core/` stays pure: no DOM, no fetch, no filesystem. Texture _definitions_ and contrast arithmetic are data and arithmetic and may live there; anything that calls `document`, `getComputedStyle` or `createPattern` lives under `src/ui/`.
2. The worker owns the genotype matrix and never sends it back (docs/adr/0001). M2.5 adds no worker request and changes no result shape. `GenotypeClassesData` is reordered on the main thread, never re-requested for a reorder.
3. No column name, parameter name or output format documented in docs/data-formats.md changes. M2.5 touches no exporter's columns and no parameter; `scripts/make-fixture.mjs` and `tests/fixtures/synthetic/` are not modified. The fixture gate is still run per commit; on this milestone it cannot fail for a reason M2.5 introduced, and a failure means something outside scope was touched.
4. The Okabe-Ito class colours in src/core/palette.ts do not change. Their encoding gains a second channel (a texture); the hex values are untouched and the report legend keeps them.
5. The ADR 0009 open question, whether to fill marker intervals where the flanking markers disagree, stays open and outside M2.5. `fillBetweenMarkers` in src/ui/canvas/binning.ts is not modified in any phase. The minority overlay of phase 3 is defined so that it never applies to a column that `fillBetweenMarkers` extended, so it makes no claim about the genome between markers either.
6. Four gates pass before every commit: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`; plus `npm run fixture` followed by `git diff --exit-code -- tests/fixtures/synthetic`.
7. Every colour and dimension lives in a CSS custom property in `src/ui/tokens.css`. No literal colour or dimension appears in a component file, where "component file" means `src/App.tsx` and every `.tsx` under `src/ui/`. The mechanical gate is the ESLint rule of phase 1. Canvas geometry modules (`src/ui/canvas/*.ts`) and the self-contained report (`src/export/report.ts`) are outside the gate by construction: the renderer receives its colours and font from the screen (phase 5), and the report must stay self-contained and cannot reference the app stylesheet.
8. Conventional Commits; phases 2 to 5 are user-visible and each adds a `CHANGELOG.md` entry under `[Unreleased]`. Phase 1 is not user-visible and adds none. No AI attribution in commit messages (CLAUDE.md).

## How the lint gate coexists with five commits

The literal-value gate must fail on a literal from commit 1 onward, but `src/App.tsx` and the six screens hold about thirty-five literal lines today and moving them is phase 5's work. The resolution is an explicit, enumerated allowlist of legacy files in `eslint.config.js` that shrinks each phase and is deleted in phase 5. Any file not on the list is gated in full from phase 1. This is a scoping mechanism, not a change of phase order; a file that has been migrated can never regress because it is removed from the list in the same commit that migrates it.

| phase | files removed from the allowlist                                                                                 |
| ----- | ---------------------------------------------------------------------------------------------------------------- |
| 1     | (list created: `src/App.tsx`, `src/ui/screens/{Upload,Summary,LineTable,GenotypeView,Compare,Export}Screen.tsx`) |
| 2     | none (new files are gated; the two edited screens stay listed)                                                   |
| 3     | none                                                                                                             |
| 4     | `src/ui/screens/LineTableScreen.tsx`                                                                             |
| 5     | every remaining entry; the constant is deleted                                                                   |

### Token contract

This is the complete list. Later phases code against these names and add none without amending this table. Values are given as they appear in `tokens.css`; every colour is written as six-digit uppercase hex or `rgb(... / alpha)`; every dimension carries its unit.

The regexes match `#ffffff` and `'12px'` and leave `href="#main-content"` alone because `m` is not a hex digit. Percentages, `em`, unitless `flex` strings and computed values (`style={{ height: `${pct}%` }}`, `style={{ background: classSwatchCss(cls) }}`) pass; a bare number inside `style` does not, so a component that needs a computed pixel size builds it from a token via `calc()` in CSS instead.

### Acceptance

`tests/tokens.test.ts` reads `src/ui/tokens.css` with `node:fs` and asserts, from the text alone: exactly twelve `--neutral-N` declarations; each is six-digit hex with `r = g = b`; `relativeLuminance` strictly decreases from step 1 to 12; `contrastRatio(neutral-12 | 11 | 10, neutral-1..5) >= 4.5` for every pair; `contrastRatio(neutral-9, neutral-1..5) >= 3`; `contrastRatio(neutral-12, neutral-1..5) >= 3` (focus ring); `contrastRatio(neutral-1, neutral-12) >= 4.5` (text on solid); the spacing declarations are exactly 4, 8, 12, 16, 24, 32, 48 px; the three row heights are exactly 28, 32, 40 px; `--text-ui` is 13px and `--text-body` 14px; and every hex literal in the file appears on a `--neutral-N` line (no colour hides in an alias).

`tests/lint-gate.test.ts` constructs `new ESLint({ overrideConfigFile: true, overrideConfig: [...] })` with the TypeScript parser, JSX enabled and `no-restricted-syntax` set from the JSON, then `lintText` on a probe whose `filePath` is `src/ui/screens/Probe.tsx` containing one hex string, one `px` string, one hex inside a template literal, and `style={{ width: 240 }}`; asserts four messages with `ruleId === 'no-restricted-syntax'`. A second probe using only `className` and `var(--space-4)` yields zero messages.

`tests/contrast.test.ts` asserts `contrastRatio('#FFFFFF', '#000000')` is 21 and `relativeLuminance('#0072B2')` is 0.152 to three places, and that a three-digit or malformed string throws.

Lint over the whole tree passes with the allowlist in place; typecheck, test and build pass; the fixture diff is empty.

`src/ui/lines/line-order.ts`:

```ts
export type LineSortColumn =
  | 'sampleId'
  | 'lineName'
  | 'generation'
  | 'familyId'
  | 'rppCount'
  | 'rppBp'
  | 'rppCm'
  | 'nSegments'
  | 'largestSegmentMb'
  | 'flags'
  | `target:${number}`;

/** React Aria's SortDescriptor vocabulary, so phase 4 maps one-to-one. */
export type SortDirection = 'ascending' | 'descending';

export interface LineSort {
  column: LineSortColumn;
  direction: SortDirection;
}

export interface LineFilter {
  /** Case-insensitive substring over sampleId, lineName, generation, familyId and each flag. Empty matches everything. */
  text: string;
  flaggedOnly: boolean;
  /** Restrict to the selection; preserves the M2 behaviour of the genotype view drawing only selected lines. */
  selectedOnly: boolean;
}

export const EMPTY_LINE_FILTER: LineFilter;

/**
 * Filter, then sort. Numeric columns place NaN last in both directions.
 * String columns use localeCompare with { numeric: true } so NIL_2 sorts
 * before NIL_10. `target:i` compares targetStatus[i] ?? ''. `flags` compares
 * flags.join(' '). Sort is stable: ties keep `rows` order. sort === null
 * returns the filtered rows in `rows` order.
 */
export function orderLineRows(
  rows: readonly LineRow[],
  sort: LineSort | null,
  filter: LineFilter,
  selected: ReadonlySet<string>,
): LineRow[];

/** total = rows.length; visible = visible.length; selected = count of ids in `selected` that occur in `rows` (hidden selected rows still count). */
export function lineCounts(
  rows: readonly LineRow[],
  visible: readonly LineRow[],
  selected: ReadonlySet<string>,
): { total: number; visible: number; selected: number };
```

### State added to App.tsx

```ts
const [lineSort, setLineSort] = useState<LineSort | null>(null);
const [lineFilter, setLineFilter] = useState<LineFilter>(EMPTY_LINE_FILTER);
// `selected: Set<string>` already exists and is unchanged.

const lineRows = useMemo(
  () =>
    rpp === null || loaded === null
      ? []
      : buildLineRows({ rpp, samples: loaded.samples, segmentsByCandidate, targets, qc }),
  [rpp, loaded, segmentsByCandidate, targets, qc],
);
const visibleLineRows = useMemo(
  () => orderLineRows(lineRows, lineSort, lineFilter, selected),
  [lineRows, lineSort, lineFilter, selected],
);
const visibleSampleIds = useMemo(() => visibleLineRows.map((r) => r.sampleId), [visibleLineRows]);
const counts = useMemo(
  () => lineCounts(lineRows, visibleLineRows, selected),
  [lineRows, visibleLineRows, selected],
);
const regions = useMemo(() => targets?.regions ?? [], [targets]);
```

`runLoad` additionally resets `lineSort` to `null` and `lineFilter` to `EMPTY_LINE_FILTER` next to the existing `setSelected(new Set())`.

The classes fetch effect changes in two ways: it requests `visibleSampleIds` (not "selection or all"), and `classesKey` is `classesRequestKey(visibleSampleIds)`. The request itself sends the ids sorted; the worker returns lines in request order (src/workers/analysis.worker.ts, `case 'classes'`), and display order is applied on the main thread:

```ts
const orderedClassesData = useMemo(
  () => (classesData === null ? null : permuteClassesData(classesData, visibleSampleIds)),
  [classesData, visibleSampleIds],
);
```

Export receives the same data: the report's figures are the lines the genotype view is showing, in the order it shows them. This replaces the M2 rule "selection, else all"; the equivalent of the old behaviour is `lineFilter.selectedOnly`. ### Definitions (pure, in src/core/palette.ts)

```ts
export type TextureKind = 'plain' | 'rising' | 'falling' | 'crosshatch' | 'dots';
export interface ClassTexture {
  kind: TextureKind;
  /** Stroke or dot colour. */
  ink: string;
  /** Stroke width, CSS px. */
  strokeWidth: number;
  /** Perpendicular distance between strokes, or dot grid pitch, CSS px. */
  pitch: number;
}
export const TEXTURE_INK = OKABE_ITO.black;
export const CLASS_TEXTURES: Record<CallClassValue, ClassTexture>;
/** CSS `background` shorthand value drawing the texture over the class colour, for legend swatches on screen and in the report. */
export function classSwatchCss(cls: CallClassValue): string;
```

| class         | colour (unchanged) | kind       | geometry                                  | ink       | width | pitch |
| ------------- | ------------------ | ---------- | ----------------------------------------- | --------- | ----- | ----- |
| RP_HOM        | `#0072B2`          | plain      | none                                      |           |       |       |
| DONOR_HOM     | `#D55E00`          | rising     | lines from bottom-left to top-right ("/") | `#000000` | 1 px  | 4 px  |
| HET           | `#F0E442`          | falling    | lines from top-left to bottom-right ("\") | `#000000` | 1 px  | 4 px  |
| NONPARENTAL   | `#CC79A7`          | crosshatch | both diagonals                            | `#000000` | 1 px  | 4 px  |
| MISSING       | `#FFFFFF`          | dots       | one 1 x 1 px square at each grid point    | `#000000` | 1 px  | 4 px  |
| UNINFORMATIVE | `#D9D9D9`          | plain      | none                                      |           |       |       |

One ink for every texture. Black was measured against every class fill: 4.05:1 on recurrent blue, 5.43 on donor vermilion, 15.88 on heterozygous yellow, 6.86 on nonparental purple, 21.0 on missing white; every textured class clears 3:1 with margin, and a minority overlay drawn in black clears 3:1 on any majority fill, which a white ink would not (white on yellow is 1.32:1). Geometry carries identity, ink carries contrast.

Two classes are plain. This is a departure from the sentence "every genotype class gains a texture" in ADR 0009 and is listed at the end. The argument: recurrent parent covers most of a near-isogenic line, so texturing it would texture the whole canvas and the departures from it would stand out less, not more; uninformative is the track background and is not a call. The two plain fills separate by 3.67:1 in luminance (0.152 against 0.694), so in greyscale they remain distinct from each other, and every other class is textured. In greyscale the six read as: dark plain (RP), mid with rising lines (donor), light with falling lines (het), mid with crosshatch (nonparental), white with dots (missing), light plain (uninformative).

CSS equivalents in `classSwatchCss` (angles are CSS gradient angles, where stripes run perpendicular to the gradient line, so `135deg` yields rising "/" stripes and `45deg` falling "\" stripes):

- rising: `repeating-linear-gradient(135deg, INK 0 1px, transparent 1px 4px), FILL`
- falling: `repeating-linear-gradient(45deg, INK 0 1px, transparent 1px 4px), FILL`
- crosshatch: both gradients, comma-separated, then `FILL`
- dots: `radial-gradient(circle at 0.5px 0.5px, INK 0.5px, transparent 0.6px) 0 0 / 4px 4px repeat, FILL`
- plain: `FILL`

### Pattern builder (DOM, in src/ui/canvas/textures.ts)

```ts
export type ClassPatterns = Record<CallClassValue, CanvasPattern | null>; // null for plain
export function buildClassPatterns(ctx: CanvasRenderingContext2D, dpr: number): ClassPatterns;
```

For each textured class: a tile canvas of side `s` device pixels where `s = round(pitch * sqrt(2)) * dpr` for rising, falling and crosshatch (so the perpendicular spacing is the declared pitch) and `s = pitch * dpr` for dots; strokes of width `strokeWidth * dpr`, `lineCap: 'butt'`, rising as the line (0, s) to (s, 0), falling as (0, 0) to (s, s), crosshatch both, dots as `fillRect(0, 0, dpr, dpr)`. `ctx.createPattern(tile, 'repeat')`, then `pattern.setTransform(new DOMMatrix().scale(1 / dpr))` so the pattern is crisp under the renderer's `setTransform(dpr, ...)`. Patterns are anchored at the canvas origin, so adjacent runs tile continuously. The renderer caches the result per `dpr`.

### Second channel from binning

```ts
export interface BinnedColumns {
  /** As binMajorityClasses returns today, including the fillBetweenMarkers extension. */
  majority: Uint8Array;
  /** Per column: the called class with the second-highest count when at least two called classes are present, else 255. Ties by ascending class code. Never extended across empty columns. */
  minority: Uint8Array;
```

MISSING and UNINFORMATIVE never appear in `minority`, for the same reason they do not compete for the majority. A column that `fillBetweenMarkers` extended from a neighbour carries no minority, because the minority describes markers that landed in that column and an extended column holds none; this keeps the overlay from asserting anything between markers (invariant 5). Zoomed in far enough that each column holds one marker, no column has a minority and no overlay is drawn, which is correct: nothing is hidden.

### Compositing in the renderer

In `draw()`, per chromosome track, `binClassesWithMinority` replaces `binMajorityClasses`. The existing run-merging loop over `majority` now does, per run of class `c`: `fillStyle = CLASS_COLORS[c]; fillRect(...)`, then if `patterns[c] !== null`: `fillStyle = patterns[c]; fillRect(...)` over the same rectangle. A second run-merging pass over `minority` draws, per run of class `n !== 255` with `patterns[n] !== null`, `fillStyle = patterns[n]; fillRect(...)` over the run. Because RP_HOM is plain, a recurrent minority inside a donor bin draws nothing; the case ADR 0007 records, a non-recurrent call hidden inside a recurrent bin, is drawn as the recurrent fill overlaid with the minority's pattern. ## Dependency check on the phase order

The order stands. Two places would have been violations without the mechanisms above and are worth knowing:

1. Phase 1's gate versus the untouched screens: resolved by the enumerated allowlist rather than by pulling phase 5's migration forward or weakening the rule to a warning.
2. Phase 2 puts an action bar on the genotype screen before phase 4 rebuilds it on React Aria and before phase 5 styles it. The phase 2 version is native, unstyled controls in a new file that passes the gate; about forty lines are replaced in phase 4. The alternative, deferring the reverse direction of the sort criterion to phase 4, would leave phase 2 unable to demonstrate its own acceptance.

Phase 3 depends on nothing in phase 2 and could be swapped with it; it is left where the maintainer placed it. Phase 4 depends on phase 1 (tokens, React Aria) and phase 2 (`LineSort` vocabulary, the visible-rows selection rule). Phase 5 depends on all four.

## Inconsistencies and conflicts to settle before implementation

1. **"Every genotype class gains a texture"** (ADR 0009; the brief says "each class") versus this specification, which leaves RP_HOM and UNINFORMATIVE plain with the argument and the 3.67:1 measurement given in phase 3. If the maintainer wants all six textured, RP_HOM takes a horizontal 1 px black stripe at 4 px pitch and the minority rule changes so an RP minority is also drawn; nothing else in the spec moves.

2. **Chrome already carries hue today**, in two places ADR 0009 forbids: `src/ui/screens/SummaryScreen.tsx` line 152 fills the call-rate histogram with `#0072B2`, which is the recurrent-parent class colour, and line 181 tints flagged rows `#fde0dc`; `src/App.tsx` uses `#005fcc` for focus. Phase 5 replaces all three with neutrals. A consequence the brief does not discuss: with no hue anywhere in chrome, error and warning states are carried by position and weight alone (the alert bar). If that proves too quiet in use, the fix is one reserved hue chosen against Okabe-Ito, and that is a decision, not a token edit.

3. **Density table in the brief** gives vertical cell padding as 7 px top and 6 px bottom, which with 13 px type at 1.4 line height sums to 32 px and to nothing else; it cannot produce 28 or 40. This spec makes row height the token and derives padding, and records the brief's figure as the basis for the default only.

4. **"Labels in a fixed left gutter"** (ADR 0009, brief) describes something that does not exist yet: labels are drawn inside the canvas at `labelWidth: 120` and are not reachable by assistive technology. After phase 5 two label mechanisms coexist: DOM buttons on screen, canvas text in the report's PNG figures (which still use `system-ui`, since the report embeds no font). That is acceptable but should be stated in the M2.5 verification block.

5. **PLAN.md's M2.5 sentence** lists React Aria "for table, menu, dialog and form behaviour". The application has no menu and no dialog today and M2.5 adds none; phases 4 and 5 use table and form controls only. This is not a gap, but the sentence overstates what ships.

6. **The canvas's drawing rule** under a shared selection model is not specified by ADR 0009. M2 draws the selection, or every candidate when nothing is selected, and the report follows. This spec draws the visible rows in display order and offers `selectedOnly` as a filter (phase 2). The maintainer should confirm this reading before phase 2, because Export inherits it.

7. **Natural sort order.** Phase 2 changes string sorting to `localeCompare(..., { numeric: true })` so `NIL_2` precedes `NIL_10`; today it does not. It is what a breeder expects from R's `mixedsort` but it is a behaviour change and is named in the changelog.

8. **ADR 0009's "border-weight change"** for selection shifts layout if implemented as a border; phases 4 and 5 use an inset box-shadow of the same width, which is the same appearance.

9. **CLAUDE.md is stale in two lines**: it says "0008 is the most recent" ADR (0009 exists) and "M3 is next" (PLAN.md now lists M2.5 before M3). Both belong in the docs commit after phase 5.

10. **Attribution.** CLAUDE.md forbids `Co-Authored-By` and generated-with footers in commits and pull requests. Any session tooling that appends attribution must be overridden for this repository; the five commit subjects above are written without it.

11. **The gate's boundary** is `src/App.tsx` plus `src/ui/**/*.tsx`. `src/ui/canvas/*.ts` and `src/export/report.ts` hold literals by design (phase 5 moves the renderer's on-screen values behind `RendererTheme`; the report is self-contained). If the maintainer wants the `.ts` canvas modules gated too, the only remaining literals after phase 5 are `DEFAULT_LAYOUT` and `DEFAULT_THEME`, and gating them means the report must read its theme from somewhere that is not the DOM.

12. **The brief's Flapjack gutter is 100 px; this spec keeps 120 px** because that is what the renderer draws today and sample ids in the fixture fit it. The token makes the choice reversible.

13. **Environment.** `react-aria-components` is not installed (no `node_modules/react-aria-components`), so its version, its behaviour under `exactOptionalPropertyTypes`, and whether its `Table` renders under `renderToString` in `environment: 'node'` are unknown until phase 1's `npm install`. `public/` does not exist, so fonts are referenced by CSS `url()` under `src/` and Vite hashes them, which is also what makes `VITE_BASE_PATH` safe. `vite.config.ts` includes only `tests/**/*.test.ts`; phase 4 widens it for `.tsx` tests.
